# Court Board is a public-write Lab without Sign-in

Every Lab so far (Job OS, WMW) is private to the Site Admin: Cognito admin-only sign-in, Amplify Data models authorised for `authenticated` only. Court Board ([CONTEXT](../court-board/CONTEXT.md)) breaks that pattern on purpose. Its Players are 25+ colleagues and guests who will not create accounts, and its Organisers are a committee, not Site Admins. This ADR records how a public page takes writes without weakening the rest of the site.

- **No Sign-in for Players or Organisers.** Cognito stays admin-only (`allowAdminCreateUserOnly`); Court Board adds no user pool users and no self-sign-up. The Site Context’s “Individual Labs remain gated” is amended: Court Board’s Signup and Organiser links are capability URLs, not Sign-in.
- **Trust, not verification.** A Player enters phone number, name and Tier (Employee, Alumni or External) and is believed. Guest seats (at most two) take a name and a Tier of Alumni or External. Organisers can correct a Seat’s Tier; the Order recomputes. The phone number is the identity that Penalties attach to, not a proof of who someone is.
- **Capability links, stored as hashes.** A Session has a public Signup link; a Club has a secret Organiser link (≥128 bits of randomness). The database holds only SHA-256 hashes of Organiser tokens, so a leaked table does not leak Organiser rights. Rotating the link invalidates the old one.
- **All writes go through Server Actions; no public API.** The browser never receives AppSync or DynamoDB credentials, and there is no `publicApiKey` or guest IAM access to Court Board data. Server Actions (the same pattern as WMW’s Workbook pull) validate input, apply the rules, and write to a dedicated DynamoDB table defined in `amplify/backend.ts` and granted only to the Hosting compute role. Court Board does not add models to the Job OS `a.schema`.
- **The Order is computed, never stored.** A pure function in `src/lib/court-board/` turns Seats, Penalties, Club rules and the current time into the Main list and Waitlists. Release needs no scheduler: it is the clock passing a time. The function is unit-tested against real past Sessions.
- **Phone numbers are international, normalised to E.164, in one box.** There is no separate country-code field. The Player types or pastes a number in any form (`+` or `00` prefix, spaces, dashes, brackets). As they type, `libphonenumber-js` (`AsYouType`, small `min` metadata) formats it, shows the detected country's flag in the box, and turns the box green once the number is valid. A number without a country prefix is read as UK (+44), the Club's default region. The browser check is feedback only: the server parses and validates again and stores the E.164 form (`+447700900123`), so `07700 900123`, `+44 7700 900123` and `0044 7700900123` are one Player. An invalid number is rejected with a plain message.
- **Phone numbers are a keyed hash.** The E.164 string is HMAC-SHA256'd with a server secret held in Hosting secrets / SSM. A plain hash is rejected because a country's mobile number space is small enough to reverse in minutes. The last three digits may be stored in clear so Organisers can tell two Players with the same name apart. Numbers are never rendered publicly.
- **A 6-digit PIN protects each Player, on any device.** The first time a phone number takes a Seat, the Player chooses a PIN. After that, taking a Seat with that number, cancelling, or changing name or Tier needs phone number + PIN, from any phone or laptop. A typed phone number alone grants nothing. The PIN is stored as scrypt over an HMAC with a server-side pepper, so a leaked table alone cannot be brute-forced offline. Because a million guesses is a small space online, wrong attempts are rate-limited per phone number (5 tries, then a 15-minute lock that doubles each time) and per IP. A forgotten PIN is reset by an Organiser, which clears it so the Player sets a new one on their next signup. No cookies, so nothing ties a Player to one browser.
- **Abuse limits.** Per-IP and per-Session rate limits held in the same table with a short TTL; a honeypot field on the signup form; display names length-limited and rendered as text. Signup and Organiser pages are `noindex` and stay out of the sitemap.
- **Minimal retention.** Seats expire (DynamoDB TTL) eight weeks after their Session. Penalties expire at their end date. A Player record holds only the phone hash, PIN hash, last display name and last Tier.
- **Fees and payments are out of scope.** Committee members arrange them individually; the lab stores no amounts or Paid marks.

Rejected: Cognito accounts for Players (friction kills adoption: the WhatsApp thread is one tap); an Organiser-kept Roster as the source of Tier (a standing admin chore for a club that already runs on trust); an Amplify Data `publicApiKey` mode (the key ships to every browser and authorises the whole model, so rules would be client-enforced); guest IAM via the identity pool (same problem, finer grain); a WhatsApp bot (unofficial libraries break WhatsApp’s terms, and the official Groups API caps groups at 8 participants); SMS verification for phone numbers (cost and bloat for a club of 30; revisit if impersonation happens); a per-browser Seat cookie (Players could not cancel from a different device).

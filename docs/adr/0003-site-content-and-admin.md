# S3 Site Content and Admin vs Labs

Site Content (blog markdown, manifests, portfolio and blog images) lives in Amplify Storage with public read and authenticated write. The Site Admin manages it through **Admin** at `/admin`, not through Labs. Sign-in is site-wide at `/login`; each Lab consumes that session but remains a standalone product with its own shell and data (e.g. Job OS Bodies). Posts on the site are publish-ready only — drafts are not a Site Content concept. Admin supports add, edit (replace markdown/hero/metadata, change slug with no old-slug redirects), and delete for Posts. Images in Site Content are **WebP only** (one file per Photo; hero WebP for Posts). Public pages read Site Content **live** from storage (revalidate after Admin writes); a frontend deploy is not required to publish. Missing/unavailable Site Content yields **empty** public lists (CI/local safe); production content is loaded **manually via Admin** after deploy (no bulk import script). A **fallback image** for Posts without heroes remains **committed site chrome** under `public/` (not an Admin Photo). Home photography teaser should read from portfolio Site Content, not that fallback file. **`/login` and `/admin` are noindex and omitted from the sitemap**. **`blog/index.json` is authoritative** for Post list metadata; uploaded frontmatter may prefill Admin only. Admin v1 manages **Posts and Photos only** — not marketing page copy in `src/data`. In-body markdown images and variant derivation are out of scope for this stage. Rejected: content under `/labs`, Owner-named auth, footer sign-in as the entry point, DynamoDB as the content catalogue for v1, on-site draft Posts, slug redirect/history, body-image rewrite, non-WebP / multi-variant ingest, deploy-only content updates, frontmatter as the live catalogue, Admin editing of page JSON copy in v1, shipping production Posts/Photos in git, indexing Sign-in/Admin as marketing pages, an automated content import pipeline, and managing the blog fallback as portfolio Site Content.
